# 知見の還元（backport / harvest）手順 — テンプレ保守者向け

具体的な案件（生成したポスター/チラシ）で得た学びを、このテンプレ原本に戻すための手順。
下流での *抽出*（harvest）と、ここでの *適用*（apply）の2段階に分かれる。

```
poster_template ──(new-poster.ps1)──▶ 案件フォルダ（自己完結）
      ▲                                      │
      │                                      │ 制作で学びが溜まる
      │  ③ 適用（このリポで）                 ▼
      └──────── ② 受け渡し ◀── ① harvest（案件側で _backport-inbox を生成）
```

案件は **コピー由来の自己完結プロジェクト**（フォークでも参照でもない）。テンプレ更新は自動伝播しない代わりに、
学びはこの明示手順で一方向に集約する。各案件には来歴（生成元テンプレの commit）が `docs/PROJECT_LOG.md` に
刻んであり、「どの版から派生したか」を適用時の差分基準に使える。

---

## ① harvest（案件側）

案件の完成時または大きな節目で、下流エージェント／作業者が
`_backport-inbox-from-<案件名>.md` を生成する。作り方は案件に同梱の **`docs/HARVEST.md`** に従う
（汎用知見と案件固有を仕分け、出典 commit を引用、派生元テンプレ版を明記）。

## ② 受け渡し

そのノートをこのテンプレリポに持ち込み、`docs/` 直下に置く
（処理待ちの印として接頭辞 `_backport-inbox-` を付ける）。

## ③ 適用（このリポをルートにしたセッションで）

1. **独立に裏取りする。** ノートを鵜呑みにせず、案件の git 履歴・実コードを実際に見て各項目を検証する
   （過去に、ノートの「stale artifact 修正」「oklch 採用」が実態とズレていた例がある）。
2. **仕分ける。** 各項目を「汎用 → テンプレに反映」か「案件固有 → 却下」に判断する。スコープを広げる判断
   （例：別形式の正式サポート）は安易にしない。
3. **spec-first。** 仕様変更を伴うものは `poster_spec.md` を先に更新してから本体・scaffold を直す
   （`AGENTS.md`「原本を編集するときのルール」）。固定項目の既定値は安易に変えない。
4. **検証する。** 変更後に `node tools/lint.mjs`。見た目・収まりに関わるなら `node tools/render.mjs` で
   ページ数と実測高さも確認する。
5. **根拠を残す。** 採否の判断と理由を `docs/DECISIONS.md` に1エントリ記録する（後で「なぜ」が辿れるように）。
6. **消化したら消す。** 反映済みの項目はノートから削除し、全部消化したらノート自体を削除する。

来歴の使い方：ノートに書かれた派生元 commit と現テンプレ HEAD を比べると、「その案件が分岐して以降に
テンプレ側で既に入った変更」と「本当に新規の学び」を切り分けられる。
